# 项目亮点笔记：高并发 / 高可用 / 安全性

> 简单问答整理，按真实代码回答"这些能力做没做、做在哪"。这部分能力大多不在 `consumer` 服务，分布在 `trade`（下单执行）、`market`（行情/安全检测）里，会标清楚具体是哪个服务。找不到证据的一律写"未找到实现"，不按"应该有"去猜。

## 一、高并发 / 高可用 / 兜底 / 削峰

**怎么削峰？**
`consumer` 解析出交易后不是直接同步调用下游接口，而是丢进 **Kafka**（`consumer/internal/logic/mq/producer.go`，`sarama.SyncProducer`），下游 `market` 和 `dataflow` 服务各自用**独立的 Kafka 消费者**异步消费：
- `market/internal/mqs/consumers/trade_consumer.go`（用 `github.com/segmentio/kafka-go`）
- `dataflow/internal/mqs/consumers/trade_consumer.go`

这就是典型的"队列削峰"：链上交易量突然暴涨时，Kafka 先把消息缓冲住，下游按自己能处理的速度慢慢消费，不会被突发流量直接打垮。

**怎么做高并发？**
用的是 goroutine + worker pool 这一套，但**不同服务做得不一样**：
- `consumer` 里 `block/block.go:41,69,78` 创建了一个 `ants.NewPool(5)`，但全仓库搜索没有一次 `Submit` 调用——**是没用起来的死代码**，真正的并发靠开多个 `BlockService` 实例（配置 `Consumer.Concurrency`）。
- `trade` 服务的 worker pool 是真用了的：`trade/internal/svc/servicecontext.go:57` `ants.NewPool(0)`（容量 0 表示不限制），而且配了优雅退出：
  ```go
  proc.AddShutdownListener(func() {
      pool.ReleaseTimeout(30 * time.Second)
  })
  ```
- `market` 服务的 K 线缓存计算也用了 worker pool：`market/internal/cache/kline.go:98` `ants.NewPool(10)`、`market/internal/cache/klineredis.go:330` `ants.NewPool(30)`。

**怎么做高可用？**
- **RPC 层**：`consumer` 的 `ServiceContext.GetSolClient()`（`consumer/internal/svc/servicecontext.go:131-138`）对多个节点地址做**轮询**，但不检查上一次调用有没有报错、不会跳过坏节点——是负载均衡，不是真正的故障转移（failover）。当前配置实际上也只填了 1 个节点地址，轮询没有实际效果。
- **进程重连**：`consumer` 的 Solana WebSocket 断线会自动重连（`slot/ws.go:97-120`），但只覆盖两种错误类型（含 "close"/"broken pipe" 字样），别的错误类型不会触发重连。
- **优雅退出**：`proc.SetTimeToForceQuit(30*time.Second)`（`consumer.go:35`）+ 各服务的 `proc.AddShutdownListener`，这部分做得比较完整。

**怎么兜底？**
现有的兜底手段主要是"重试"，但覆盖范围有限：
- `getBlock` 失败重试最多 10 次、固定间隔 1 秒（`consumer/internal/logic/sol/block/price.go:29-61`）。
- 交易滑点超限后自动放宽滑点重试最多 3 次（`trade/internal/logic/createmarketorderlogic.go:358-367`，下面滑点部分详细讲）。
- Jito 提交遇到限流会自动重试（`trade/internal/chain/solana/jito.go:115-140` `SendViaJitoRetry`）。
- **明确没做到的兜底**：`consumer` 里失败 slot 的自动恢复链路是断的（`errorCh` 从没 `make`、消费者代码被注释，详见 `Consumer学习笔记-课程对照与代码审计.md` 第六节），这是当前项目在"兜底"这件事上最大的缺口。

## 二、用户交易安全怎么保障

**下单前的安全阀门：`SimulateOnly`**
`trade` 服务支持一个"只模拟不真发"的开关：
```go
SimulateOnly bool `json:"simulate_only,optional,env=SIMULATE_ONLY"`   // trade/internal/config/config.go:14
```
真正发交易之前会先调用 `SimulateTransactionWithOpts`（`trade/internal/chain/solana/txManager.go:502`）模拟执行一遍，如果 `SimulateOnly=true` 就到此为止不真的广播（`txManager.go:546`）——这是一个**部署环境级别**的安全阀门（比如联调、灰度阶段用），不是"每一笔交易都强制先模拟"的常态化风控。

**成交结果的安全保障：滑点保护**
见下面第四节，本质是"设置一个最低能接受的成交数量，链上不满足就直接回滚"，这是保障用户不会"越滑越亏"的核心机制。

## 四、MEV 攻击怎么处理

**Jito——已实现，在 `trade` 服务**
`trade/internal/chain/solana/jito.go` 是一套完整的 Jito 集成：
- `SendViaJito`/`SendViaJitoRetry`/`SendViaJitoBundles`（100-166行）：把交易通过 Jito 的私有通道提交，不进公开的 mempool，避免被夹（三明治攻击）。
- `queryJitoRpc`/`updateJitoFloorFee`（48-96行）：定时轮询 Jito 的小费下限（tip floor），动态决定给多少小费。
- `SendViaJitoRetry` 专门处理 Jito 限流错误码 `JitoRateLimitCode = "32097"`，遇到限流会重试。

是否走 Jito 由 `isAntiMev` 参数控制（`txManager.go:558` `if isAntiMev && tm.JitoClient != nil { ... }`），如果 Jito 没配置（比如 devnet），会自动退回普通 RPC 发送而不是直接报错（`txManager.go:567-568`）。

## 六、滑点怎么处理

**链上保护：`minAmountOut`（最低可接受成交量）**
不管走 Pump.fun 还是 Raydium（CPMM/CLMM），构造交易时都会算一个"最少要拿到多少"，塞进指令参数里：
```go
minAmountOut, amountOut, err := trade.CalcMinAmountOutByPrice(in.Slippage, ...)   // trade/internal/chain/solana/pump.go:460, raydium.go:57,127,241
```
这个值最终会变成 Raydium 指令里的 `OtherAmountThreshold`/`MinimumAmountOut` 字段（`raydium.go:96,163,265`）——如果链上实际成交数量达不到这个下限，**交易本身会失败/回滚**，这是滑点保护的根本机制（协议层面强制的，不是靠应用层事后检查）。

**自动滑点怎么实现的？——链下自动重试，会员范围有限**
`trade/internal/logic/createmarketorderlogic.go:358-367`：
```go
for tryTimes == 0 || (param.IsAutoSlippage && errors.Is(err, xcode.SlippageLimit) && tryTimes < 3) {
    ...
    switch tryTimes {
    case 1:
        param.Slippage = 4500   // 45%
        l.Info("AutoSlippageRetry")
    case 2:
        param.Slippage = 7000   // 70%
        l.Info("AutoSlippageRetry")
    }
}
```
逻辑是：先按用户设置的滑点发一次；如果链上返回的错误信息匹配"滑点超限"（`createmarketorderlogic.go:428` 判断 `strings.Contains(result, "slippage")` 或 `"TooLittleOutputReceived"`，映射成 `xcode.SlippageLimit`），并且用户开了"自动滑点"，就把滑点直接放宽到 45%、再不行放宽到 70%，最多重试 3 次——本质是"链下发现失败原因是滑点 → 调大滑点参数 → 重新构造并再发一次交易"，不是链上有什么特殊指令，就是应用层的重试循环。
